# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Плагин Autodesk Civil 3D 2024 (.NET Framework 4.8, class library, C#) с набором
команд для проектирования армогрунтовых подпорных стен: облицовка стены,
ассоциативные разрывы коридора по профилю, извлечение материалов, поверхности
коридора. Комментарии, README и сообщения пользователю — по-русски.

Загрузка в Civil 3D командой `NETLOAD`. Точка входа `IExtensionApplication` —
`ProfCorrLink/BreakCommands.cs` (в сборке она **единственная**, второй быть не может),
поэтому она же включает оверрул ручек модуля `FaceArr` — там инициализация обоих
модулей, несмотря на имя файла.

## Сборка

```powershell
& "C:\Program Files\Microsoft Visual Studio\2022\Community\MSBuild\Current\Bin\MSBuild.exe" `
  "D:\проекты\Подпорные стены\Civil3D_commands\Civil3D_commands\Civil3D_commands.csproj" `
  /t:Rebuild /p:Configuration=Debug /nologo /v:minimal
```

- Ссылки на Autodesk ищутся свойством `AcadDir` в `.csproj` (перебор кандидатов,
  внятная ошибка через target `CheckAcadDir`). Переопределение:
  `/p:AcadDir="X:\...\AutoCAD 2024\"` — **обязательно со слешем в конце**.
  Относительные `HintPath` не использовать: они ломались при переносе на другой диск.
- `.csproj` — старого формата (не SDK-style): **новый `.cs` файл надо руками
  добавить в `<ItemGroup>` с `<Compile Include=...>`**, иначе он молча не компилируется.
- Результат — `Civil3D_commands\bin\Debug\Civil3D_commands.dll`, его и грузят
  `NETLOAD`. Конфигурация только Debug; платформа `AnyCPU` (в
  `ProfCorrLink/README.md` написано «x64» — там неверно, менять не нужно:
  AnyCPU-сборка грузится в 64-битный хост как есть).
- **Civil 3D держит DLL после `NETLOAD`.** Выгрузить .NET-сборку из сеанса нельзя,
  пересборка в `bin\Debug` падает с MSB3027. Перед сборкой попросить пользователя
  закрыть приложение (`Get-Process acad`).
- Если закрывать не хотят: компилятор пишет в `obj\Debug\Civil3D_commands.dll`
  **до** копирования, и MSB3027 срывает только копирование. Свежая метка времени
  на `obj\Debug\Civil3D_commands.dll` — доказательство, что код компилируется;
  в сеанс Civil 3D эта сборка при этом не попала.

## Проверка

**Сборка — единственная проверка, доступная агенту.** Тестов нет и быть не может:
команды интерактивны (выбор объектов мышью), `accoreconsole.exe` идёт без вертикали
Civil 3D, так что `Alignment`/`ProfileView` там не существуют, а грипсы headless
не тестируются в принципе. Проверять в чертеже может только пользователь —
подтверждать фактом можно лишь «собирается», не «работает».

**Репозиторий под git** с 8 августа 2026: ветка `main`, удалённых репозиториев нет,
история начинается с состояния на эту дату. Откат доступен —
`git diff`, `git checkout -- <файл>`, `git stash`. Вне версионного контроля
`bin/`, `obj/`, `.vs/`, `*.user`, `*.bak`, `*.dwg` и `.claude/settings.local.json`;
перед коммитом смотреть `git status`, чтобы туда не уехал чертёж или резервная
копия DLL. Незакоммиченное теряется по-прежнему, поэтому перед рискованной правкой
имеет смысл коммит, а крупные изменения делать точечным редактированием,
а не переписыванием файла целиком.

Каждая итерация стоит пользователю перезапуска Civil 3D, поэтому в одну сборку
имеет смысл класть и исправление, и диагностику, которая разделит оставшиеся
гипотезы. Для этого есть диагностические команды: `FACINGWALLDIAG` в `FaceArr` (счётчики
вызовов оверрула) и `RW_BREAKDIAG` в `ProfCorrLink` (связь, маркеры, фактические
границы областей коридора). Не удалять.

| `CorridorSurfaceCreator.cs` | Сборная солянка из семи независимых классов (~1700 строк): поверхности коридора, переименование подсборок/областей, нарезка коридора по профилю, ступени (`RW_CREATESURFACES`, `RW_RENAMESUBS`, `RW_SPLITCORRBYPROF`, `RW_ADDSTEPS`, `RW_DELETESURF`, плюс служебная `UpdateRegions`). |

| `ProfileToPlaneTransparent.cs` | Прозрачный режим `PTP`: `PointMonitor` перехватывает любой запрос точки и запускает jig «пикет → отметка → смещение». Свой namespace `ProfileToPlane`. |
| `PropertySetHelper.cs`, `PropertySetArea.cs` | Наборы характеристик (Property Sets), геосвойства, площадь тела (`RW_AddGeoPropsToPropertySet`, `GETBODYAREA`). |

## Архитектурные соглашения

**Источник истины — модель, а не геометрия чертежа.** В обоих основных модулях
данные живут в Xrecord/словаре чертежа, ссылки на объекты хранятся как Handle,
а нарисованные примитивы считаются производными и перестраиваются из модели:
`FacingWallController` для облицовки, `StationMarker` + `MarkerStore` для разрывов.

**Все правки идут через один класс-оркестратор.** В `ProfCorrLink` реактор
(`BreakReactor`) ничего не меняет сам — только помечает «грязные» маркеры и на
`CommandEnded`/`Idle` зовёт `AssociativeBreakManager` под `BreakSession.Suspend()`.
Это защита от циклов перестроения (профиль → коридор → таргеты → профиль).
Правки из реактора обязаны быть в `Document.LockDocument()`.

**Ручки (grips) вешаются на служебный `Line` с XData, а не на целевой объект.**
Проверено в Civil 3D 2024: собственные `GripData` из переопределённого
`GetGripPoints` на `BlockReference` не отрисовываются — код вызывается, грипсы
отдаются, исключений нет, AutoCAD их не рисует, причина не найдена. **Не пытаться
заново.** Рабочая схема: служебный отрезок на отдельном слое, `GetGripPoints`
не переопределяется вообще (ручки концов и середины рисует AutoCAD), перехватывается
только `MoveGripPointsAt`. Так сделано и в `FaceArr`, и в `ProfCorrLink`.

## Подводные камни API (уже наступили)

- `Overrule.AddOverrule(class, overrule, bAddAtLast)` — третий параметр это
  **позиция в цепочке**, а не «применять ко всем». `IsApplicable` AutoCAD может
  не вызывать вовсе (замерено: ноль вызовов), поэтому чужие объекты **обязаны**
  уходить в `base`. На `Line` висят оверрулы сразу двух модулей — сломать легко.
- Объект, который тянут за грипсу, уже открыт на запись грип-системой: повторно
  открыть его транзакцией нельзя, стереть тем более. Геометрию правит обработчик
  грипсы после коммита транзакции.
- `Entity` и `DBObject` есть и в `Autodesk.AutoCAD.DatabaseServices`, и в
  `Autodesk.Civil.DatabaseServices` — во всех файлах ставится алиас. `DBObject`
  всплывает реже и потому неожиданнее: например в ограничении обобщённого метода.
- `Alignment.PointLocation(station, offset, ref x, ref y)`,
  `ProfileView.FindStationAndElevationAtXY(...)`,
  `Alignment.StationOffset(...)` — параметры `ref`, не `out`.
  `StationOffset` за пределами оси возвращает NaN — оборачивать в try/catch.
  **Напрямую эти методы больше не вызывать: есть `Shared/RwGeometry`,** где
  и NaN, и исключение уже сведены к `false`/`null`. Перпендикуляр к оси там
  получается из `PointLocation(station, offset)`, а не поворотом касательной:
  численный способ врал на малых радиусах и в конце оси.
- `PromptKeywordOptions.Keywords.Add(globalName, localName, displayName)`:
  **латиницей только первый** параметр — он возвращается в `StringResult`
  и не зависит от языка. Второй и третий обязаны быть тем самым русским
  словом, которое показано пользователю. Латиница во втором параметре при
  русской подписи даёт «неправильное ключевое слово» на любой ввод, включая
  щелчок по подсказке.
- **`Keywords.Default` задаётся ГЛОБАЛЬНЫМ именем** (`"Yes"`, а не `"Да"`).
  Русское имя бросает eInvalidInput («значение не попадает в ожидаемый
  диапазон») ещё до показа запроса, и команда обрывается там, где никакого
  ввода ещё не было — искать причину будете в предыдущей строке.
  Рабочий образец обоих правил — `FacingWallCommands`.
- `PropertyDataServices.AddPropertySet` сработает, только если набор допускает
  класс объекта; см. отлаженный фильтр в `PropertySetHelper`.
